## 2026-08-16 (consultation-chat: redesigned "thinking" indicator)

- Replaced the 3-dot bouncing indicator + instant-snap step label (spec 0023) with a continuously-rotating circular spinner, a literal 3D flip animation on the label text, and a smoothly-animated bubble width — the previous version felt "overloading" once the label started changing mid-turn.
- The spinner sits structurally outside Angular's `@switch` so its animation never restarts when the label changes; the flip is gotten "for free" by keeping the label inside the `@switch`, since Angular genuinely recreates that element on every case change.
- Checked before assuming an approach: the modern CSS-only way to animate toward a `fit-content` width (`interpolate-size`/`calc-size()`) only works in Chrome/Edge today — used the reliable cross-browser alternative instead (measure the new label's width via `getBoundingClientRect()`, animate a plain `transition: width` to that value).
- Verified in a real browser with actual DOM/CSS measurements: spinner rotation confirmed monotonic across label changes (~6.83 cycles over 6.142s, matching the declared rate almost exactly), the flip animation confirmed genuinely running on a new element each time, the bubble width confirmed transitioning through real intermediate values rather than jumping.
- **Found and fixed a real bug immediately after this shipped**: longer labels ("Double-checking…", "Revising…") wrapped onto two lines instead of the bubble expanding to fit — `.step-label` had no `white-space: nowrap`, so new text wrapped to fit the container's stale width instead of overflowing, and the measurement effect never saw the true (longer) width to grow toward. Fixed with `white-space: nowrap`; also made the label bold (`font-weight: 600`) per the same feedback. Re-verified: all labels confirmed single-line (`getClientRects().length === 1`), bubble width matches the label's natural width to sub-pixel precision.
- **A second real bug found right after that fix**: lopsided spacing — a large gap before the spinner, none after the text. Both the bubble and its inner content wrapper each had their own padding, but only the inner one was measured and applied as the bubble's *total* width, so the bubble squeezed its own padding out of a number that never accounted for it, clipping the right side. Fixed by removing the inner wrapper's padding entirely and adding the bubble's actual computed padding to the measurement. Re-verified: left gap and right gap both measured exactly 12px for all three labels. 21 Angular tests pass, zero console errors. See [docs/specs/0024-consultation-thinking-indicator-redesign.md](docs/specs/0024-consultation-thinking-indicator-redesign.md).

## 2026-08-15 (fix WS stream disconnect-leak)

## 2026-07-30 (debate-thread: fix inverted agent sides + bottom-aligned avatars)

## 2026-07-19 (Redis pub/sub + WebSocket live debate streaming, backend)

- Built the backend for decision 12/13a: `WS /api/debates/{id}/stream` pushes live events (argument/status changes) the instant they happen, replacing the up-to-4-second wait `debate-thread`'s polling has today. First WebSocket endpoint and first real Redis usage in the app — both were previously provisioned (the container, the design docs) but idle.
- **A real scope decision, not a silent narrowing**: decision 12's original text asked for arguments to stream token-by-token. Directly tested against the real model before committing to a design: `ChatOpenAI(...).with_structured_output(ArgumentOutput).astream(...)` returns exactly one atomic chunk (no incremental content), while plain `.astream()` (no structured output) returns real incremental chunks for the same prompt — proving the limitation is the structured-output-and-streaming combination specifically, not streaming itself. A hand-rolled parser workaround was considered and explicitly rejected (trades a bounded, proven constraint for an unbounded, unpredictable one, and doesn't even help — the structured fields still can't show before the full text exists either way). Scoped instead to complete-event push: full ADR 0006 write-up.
- New: `redis==8.0.1` client (`core/redis_client.py`, same module-singleton shape as `core/db.py`), `redis_url` config (fail-fast, no default), publish calls added at the *existing* Activity boundaries in `debates/activities.py` (`persist_argument` → `argument_complete`, `set_debate_status`/`persist_verdict_and_close`/`mark_failed` → `status_change`) — zero changes to `DebateWorkflow`'s control flow or the LangGraph node shape. `core/security.py` refactored to share JWT-decode logic between the HTTP and WebSocket auth paths (the WS variant returns `None` on failure instead of raising, since there's no HTTP response to attach a 401 to on a socket).
- Verified against a real, currently-running debate with a real WebSocket test client (not curl — WS isn't curl-friendly the way REST is): `status_change`/`argument_complete` events arrived live, in real time, timestamps spread across the full ~26s debate run rather than batched at the end; every streamed `argument_id` cross-checked exactly against the rows that actually landed in Postgres. Invalid-token and wrong-owner connection attempts both rejected outright (HTTP 403 at the WebSocket handshake — `close()` before `accept()` aborts the protocol upgrade, same protective effect as a WS close code, just manifesting as an HTTP rejection). Two simultaneous viewers on the same debate received an identical event sequence with zero connection-manager code needed (Redis's native pub/sub fan-out). Confirmed the app fails loudly at startup with no `REDIS_URL` set, same as the existing `OPENAI_API_KEY`/`TEMPORAL_ADDRESS` checks.

## 2026-07-18 (consultant/case-submission stage, backend)

- Built the backend for the consultant stage (ADR 0005/spec 0009): a new `ConsultationWorkflow` (Temporal) — the first long-running, externally-signaled workflow in this codebase, deliberately different from `DebateWorkflow`'s fire-and-forget shape since a consultation is a live dialogue, not an unattended background process. Turns are delivered via `@workflow.update` handlers (`submit_message`, `approve`), not signal+poll: the frontend/curl caller gets a normal synchronous request/response, backed by Temporal's retry/durability guarantees underneath, without needing WebSocket/Redis infrastructure.
- `CaseTypeConfig` gained `default_consultant_persona`/`default_participant_personas`/`default_judge_persona`/`default_max_rounds` — the mechanism that lets an approved consultation auto-create a real, fully-populated `Debate` with no admin involvement (the two required FK fields fail-fast at save time if left unconfigured; empty participants fails loudly at approval time instead of silently creating a broken `Debate`). `ConsultationSession.Status` gained `FAILED`, mirroring `DebateWorkflow`'s existing `mark_failed` pattern.
- No LangGraph checkpointer used anywhere (reaffirmed, not just assumed — verified against Temporal's own docs: "Temporal handles durability, so third-party checkpointers are not needed"). Conversation history is reconstructed from Postgres before every consultant turn, the same shape `fetch_arguments` already uses for debates.
- **Found and fixed four real bugs during implementation/verification, none of them hypothetical:**
  1. Two Temporal Activities (`debates.mark_failed` and the new `consultations` one) shared the exact same function name — Temporal registers Activities by name across the *entire* Worker, not per-package, so this crashed the whole worker process at startup, not just the new code. Renamed the new one to `mark_consultation_failed`.
  2. OpenAI's strict structured-output schema mode flatly rejects a free-form `dict` field (confirmed via the actual error: every property must be enumerated with `additionalProperties: false`, which an open-ended case payload can't satisfy). Fixed by having the consultant emit the payload as a JSON-encoded string, parsed back into a real dict in `graphs.py` — a schema-layer workaround, not a data-model change.
  3. Two related "retries forever instead of failing fast" gaps, same root cause as each other: the consultant LangGraph node had no bounded `retry_policy`, so bug #2 (before it was fixed) retried 30+ times with no end in sight instead of failing after a few attempts; separately, the approval activity's business-validation errors (missing/misconfigured `CaseTypeConfig`) were retryable by default, retrying 3 times before surfacing a permanent, non-transient failure. Fixed with an explicit bounded `RetryPolicy` on the node and `non_retryable=True` on the validation errors.
  4. The router's error handling for `WorkflowUpdateFailedError` needed to unwrap a different number of `.cause` levels depending on where the underlying `ApplicationError` was raised — directly in an Update handler (one level) vs. inside an Activity it calls (two levels, wrapped in an extra `ActivityError`) — verified empirically by introspecting the actual exception objects rather than assumed; getting it wrong silently returned an unhelpful generic message ("Activity task failed") instead of the real one.
- Verified end to end via curl against the real running stack: a multi-turn negotiation correctly reflecting accumulated history, approval creating a real `Case`+`Debate`+`DebateParticipant` set matching the configured defaults exactly, message-after-approval and approve-before-ready both failing cleanly (409/400, not hanging or 500ing), IDOR checks clean on both new endpoints (a non-owning user gets a clean 404), and an integration check chaining the newly-created debate straight into the existing `/api/debates/{id}/start` endpoint through to a real `Verdict` — proving the two features actually compose, not just work in isolation.
- Explicitly out of scope, unchanged: the frontend chat UI (a separate, not-yet-started follow-up spec — no real user can drive this flow yet), Redis/WebSocket streaming for either debates or consultation chat (decision 12, still not built), cancelling/abandoning a consultation session.

  1. Angular's *built-in* XSRF interceptor silently skips cross-origin requests (verified against its source — compares request origin to page origin, no-ops on mismatch). Fixed by manually reading the `XSRF-TOKEN` cookie and attaching `X-XSRF-TOKEN` for requests to the trusted Django origin.
