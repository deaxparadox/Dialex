## Open

- [ ] Bug: `WS /api/debates/{id}/stream` never detects a client disconnect once a debate is finished, leaking the server-side task + Redis subscription forever. Repro: run any debate to completion (JUDGED/NO_CONSENSUS), close/navigate away from the browser tab, then check `redis-cli PUBSUB CHANNELS` — the `debate:{id}:stream` channel stays subscribed indefinitely; the orchestrator never logs `"stream client disconnected from debate:{id}:stream"`. Confirmed live on a real user session (consultation session 16 → debate 17, 2026-07-19): the debate itself streamed and completed correctly (WS pushes landed within single-digit milliseconds of each DB write — verified against Postgres/Temporal), but 10+ minutes after `NO_CONSENSUS`, `debate:17:stream` (and 5 other finished debates' channels: 12-16) were still live-subscribed in Redis with zero errors logged anywhere. **Root cause, read directly from `orchestrator/app/debates/router.py`'s `stream_debate`**: the handler loop is `async for message in pubsub.listen(): ... await websocket.send_text(...)` — a client disconnect is only ever discovered when `send_text()` next raises, and since nothing is ever published again to a finished debate's channel, that send never happens, so the `finally` block's `pubsub.unsubscribe()`/`aclose()` never runs. Silent, unbounded — no crash, no log line, just an ever-growing set of dead Redis subscriptions and orphaned asyncio tasks under real sustained use. Not yet spec'd or fixed — logged per user's request to hold off for now. Likely fix direction (not yet approved): race the Redis-forward loop against a `websocket.receive()` loop, cancel whichever side completes first, so a client-initiated close is detected immediately regardless of Redis traffic on that channel.

- [ ] Feature: give the consultant a reflection/internal-thinking step — it currently has none. Confirmed in `orchestrator/app/consultations/graphs.py`: `build_consultant_graph()` is a single node, one direct `ChatOpenAI(...).with_structured_output(...).ainvoke(...)` call per turn, no self-check/critique pass. Concrete evidence this causes a real quality problem, found by searching actual consultation turns for "log" (not session 16 — a **different**, still-open session, id 15, `research_debate` case type): turn 5 (user), verbatim: *"log computation task which would produce calculation result for some time, it's basically a mchine learning task"* — almost certainly a typo for "long computation task." The consultant then parroted "log computation task"/"log computation tasks" back **three more times** (turns 6, 8, 12) without ever questioning the nonsensical phrase or asking "did you mean long-running?" — exactly the shallow pattern-completion behavior a reflection step should catch.
